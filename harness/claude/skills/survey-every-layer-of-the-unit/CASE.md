- **Ambiguous?** no — one right answer. The workflow layer is where the query resolves data; omitting it is a coverage gap, not a scoping choice. Contrast `audit-the-named-section`, which applies when the user names a subdivision — here the user named the API, and the unit boundary is the block.
- **Scope chosen:** machine-scoped global — Step 1 row 1. The rule "enumerate a unit's layers before surveying an API" is worth teaching a new colleague and recurs on any repeated-unit codebase; the `~/git/mil/1_blocks` model/workflow specifics are named as an anchor in the body with an instruction to trust the directory listing when the layout differs.
- **Rule written:** verdict — before surveying an API across repeated units, `ls` one unit's layers and survey each candidate layer separately, counting call sites per layer. Secondary rule from the same case: when a layer both queries and writes the vocabulary, constrain the grep to the call site — a raw literal grep in `workflow/src` ranked `pl7.app/table/visibility` (42) near the top, but those are assignments into output specs (`3D-Structure-Based-Liabilities/workflow/src/specs.lib.tengo:54,72,94,111`), not queries.

## 2026-08-10 — "Is that common practice?" answered from a unit count and a fixed-window grep

- **Repo:** ~/git/mil/tasks/MILAB-6679-developability-designer (surveying all of ~/git/mil/1_blocks)
- **Source:** correction — the operator asked whether other blocks reuse the pattern, and my earlier characterisation was wrong

- **What I did:** Answered the first question from two bad measurements.
