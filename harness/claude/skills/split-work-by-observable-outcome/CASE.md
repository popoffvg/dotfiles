## 2026-08-04 — A single new block authored as ten per-layer TODO rows

- **Repo:** `~/git/mil/tasks/MILAB-6679-developability-designer` (spec ledger for a new Platforma block in `~/git/mil/1_blocks`)
- **Task:** Compiling the TODO ledger at the end of a spec grill, for a net-new block (python design script + Tengo workflow + block model + Vue UI) plus two prerequisite packages and two migrations of shipped blocks.
- **What I did:** Wrote a 16-row ledger, ordering it deepest-layer-first per the spec contract: `L1` residue index, `L1` scan and triage, `L1` model backend, `L1` candidates, `L1` ranking, `L2` workflow, `L2` output, `L3` model, `L4` variant table, `L4` parent view — ten rows for one new block directory. Every row below the UI was reachable only through the rows above it, so no middle row was observable by a user, a caller, or a test on its own. I derived the split from the code's layering, not from what anyone could see.
- **Correction:** > let's merge all TODOs that related to block writing into the one. Assets creating is a prerequisite
- **Evidence:** The two rows the user explicitly kept separate are exactly the two that cross an enforced boundary — `software-liability-definitions` and `assets-antifold-weights` are each their own git repo with its own release (`1_blocks/<block>/.git` exists per block; `1_blocks/` has no `.git`), and the block's script cannot read a motif or load a checkpoint until each is published. The ten merged rows crossed no boundary at all: one new directory, no existing consumer.
- **Ambiguous?** Yes — the other branch is right when the layers have consumers that already exist, when pieces cross repos or releases, or when the work is long enough that partial progress must be reviewable. A refactor across existing call sites splits; a brand-new component with no consumers does not. The user's own instruction split on exactly the repo boundary and merged everything inside it.
- **Scope chosen:** global — row 1 of the Step 1 table. Teachable to a new colleague in one sentence, and it recurs on every work breakdown: spec ledgers, ticket splits, commit plans. The `Ln` layer vocabulary is this harness's; the failure — deriving items from the code's seams rather than from observable outcomes — is not.
- **Rule written:** check — new skill `split-work-by-observable-outcome`: for each candidate item ask who observes it alone and whether it crosses an enforced boundary; either answers cleanly → own item, neither → fold it in. Includes the tipping table for both branches and the requirement that a merge move the build order into the merged item's body.
