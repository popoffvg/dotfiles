# commit-message — what a commit says

**The message answers why the commit exists; the diff already answers what it changed.** A reader
who has the diff open still cannot see the problem that forced it, the state it moves the code to,
or the option it rejected. Those three facts are lost the moment the author forgets them, so they
are the message. The subject line only names the change; the **body carries the value**.

## Format

```
<prefix>: <subject>

<body>
```

- **prefix** — `feat`, `fix`, `refactor`, `docs`, `test`, `chore` (conventional-commits set).
- **subject** — one imperative line, ≤ 72 chars, no period. What the commit does, never a file list.
- **body** — the parts below, one paragraph each. Blank line after the subject, wrapped at 72 chars.

## The body — three parts, in this order

| Part | Answers | Write it |
|---|---|---|
| **Cause** | What forced the change — the defect, the limit, the new requirement, and what breaks or stays broken without the commit. | Always |
| **Goal** | What is true after the commit that was not true before, in the reader's terms. | Always |
| **Decision** | Which other way was possible, which one was taken, and the reason it won. | Only when a real choice existed |

**Each part is one paragraph, separated by a blank line, and the parts stay in this order.** Cause
first, because it is the only part the diff can never show. Goal second, because it is the cause
answered. Decision last, because it means something only after the reader knows what was at stake.
Merging the parts into one paragraph hides which sentence is the problem and which is the choice.

**Write the Decision part only when the commit rejected a live alternative.** A real choice is one
where the other way also worked — a different data shape, a different layer, a different failure
mode. Inventing a rejected option for commits that had none adds noise; the reader learns nothing
from "the alternative was to not fix it". When the alternative is recorded as a thought note, the
body restates the reason in its own words — it does not cite the note.

## Worked example

```
fix: revoke the prior refresh token on rotation

A refresh token stayed valid after use, so one leaked token gave an
attacker access for as long as the user kept refreshing. Nothing in
the flow could end that access short of a password reset.

Each refresh now returns a new pair and revokes the token it
replaces, so a stolen token dies at the next legitimate refresh.

A short expiry on the refresh token was the other option. It was
rejected because it signs out an idle user on a normal day, and the
stolen token stays usable until it expires.
```

## Rules

- **The message reads without the notes.** Never name `spec.md`, a `TODO-N`, a thought note, or a
  ticket id in the body. A reader with only the repo must understand the commit.
- **Never restate the diff.** No file lists, no "added X, changed Y, removed Z" — that text is
  generated by `git show` and costs the reader the parts that matter.
- **One commit, one cause.** Two causes in one body mean the change should have been two commits.

When to commit, how to split, and what a user correction lands as: `impl:sub-commit.md`.

## Where the text comes from in the wm flow

**A TODO already holds the message; the implementer copies it, never re-derives it.** The TODO's
`## Commit` block carries `Title` and `Body`, both approved by the human as the last link of the
verification chain, and the ledger row's `Why` is the Cause and Goal in compressed form. The
Decision part comes from the `decision` and `impl-decision` notes the TODO obeys. Shapes:
`arch:tpl-todo.md`. When no TODO exists — a `fix`, a hot patch, a one-off — read the diff and the
conversation that asked for it, and write the three parts from there.
